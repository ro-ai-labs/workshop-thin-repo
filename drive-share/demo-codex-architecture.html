Codex/Architecture

A coding agent from OpenAI that runs locally. This map traces the primary primitives - how a turn flows from user input through tools, permission checks, and the sandbox.

Apache-2.0 Primary language · Rust Secondary · TypeScript (codex-cli, sdk) repo · openai/codex monorepo · codex-rs/ + codex-cli/ + sdk/

The five primitives

Every Codex turn is a loop: the agent proposes calls, the tool layer routes them, permissions decide what's allowed, the sandbox contains side-effects, and plugins extend the surface. Click any file path to open it locally.

Agent loop

codex-rs/core

The heart of a session: a CodexThread drives turns, holds TurnContext, and routes model output into tool calls. Sub-agents (review, explorer, …) live in a registry alongside the main role.

  • codex-rs/core/src/codex_thread.rstop-level thread; spawns turns, owns history
  • codex-rs/core/src/session/mod.rssession machinery - root of per-conversation state
  • codex-rs/core/src/session/session.rsSession: input queue, rollout, event bus
  • codex-rs/core/src/session/turn.rsone model→tool→model cycle
  • codex-rs/core/src/session/turn_context.rsresolved config + policy for the current turn
  • codex-rs/core/src/agent/mod.rsmulti-agent registry & role plumbing
  • codex-rs/core/src/agent/control.rsspawn / steer / cancel sub-agents
  • codex-rs/core/src/agent/registry.rsnamed agent lookup; built-ins live here
  • codex-rs/core/src/client.rsmodel client; what actually calls the Responses API
  • codex-rs/core/src/compact.rscontext compaction when the window gets tight

Tools

codex-rs/tools · core/src/tools

A two-layer system: the tools/ crate defines specs/dispatch types (including MCP & dynamic tools), and core/src/tools/ ships the built-in handlers - shell, apply_patch, plan, multi-agent, MCP resource, view_image, request_user_input…

03

Permissions

core/config · execpolicy · guardian

Decides what runs without asking. Profiles in config/permissions.rs resolve to per-tool decisions. The execpolicy DSL classifies shell invocations as safe/unsafe; the guardian gates the riskier ones with an approval round-trip.

  • codex-rs/core/src/config/permissions.rsuser-facing permission profiles & merge rules
  • codex-rs/core/src/config/resolved_permission_profile.rsresolved, per-turn permission snapshot
  • codex-rs/core/src/safety.rsglobal safety checks before execution
  • codex-rs/core/src/exec_policy.rswires execpolicy into the exec path
  • codex-rs/core/src/guardian/mod.rsapproval workflow: ask-before-run
  • codex-rs/core/src/guardian/review.rsguardian review pass on outputs
  • codex-rs/execpolicy/src/lib.rsDSL for classifying shell commands
  • codex-rs/execpolicy/src/policy.rspolicy assembly
  • codex-rs/execpolicy/src/decision.rsMatch / NoMatch / Forbidden outcomes
  • codex-rs/execpolicy/src/rule.rsrule language: arg matchers, capabilities
  • codex-rs/shell-escalation/src/lib.rs"escalate to user" prompt plumbing
04

Sandbox

sandboxing · linux-sandbox · windows-sandbox-rs

Three backends share one manager: seatbelt on macOS, landlock + bubblewrap on Linux, and a native Windows sandbox. The crate transforms a permission profile into a concrete policy and spawns the child under it.

  • codex-rs/sandboxing/src/lib.rscrate root, common types
  • codex-rs/sandboxing/src/manager.rspicks the backend; orchestrates spawn
  • codex-rs/sandboxing/src/policy_transforms.rspermission profile → sandbox policy
  • codex-rs/sandboxing/src/seatbelt.rsmacOS: Apple Seatbelt (.sb policies)
  • codex-rs/sandboxing/src/seatbelt_base_policy.sbplbase seatbelt policy (SBPL)
  • codex-rs/sandboxing/src/landlock.rsLinux: LSM filesystem confinement
  • codex-rs/sandboxing/src/bwrap.rsLinux: bubblewrap namespace wrapper
  • codex-rs/linux-sandbox/src/lib.rsLinux helper binary (codex-linux-sandbox)
  • codex-rs/linux-sandbox/src/launcher.rsspawn entrypoint for the sandbox child
  • codex-rs/windows-sandbox-rs/Windows backend (crate)
  • codex-rs/core/src/sandboxing/core glue: injects sandbox into shell tool

Plugins & skills

plugin · core-plugins · skills

Plugins are installable bundles (a marketplace + local store); skills are smaller in-process extensions surfaced as @-mentions. Both register dynamic tools, system prompt fragments, and MCP-style resources.
