Context Window

How the conversation/turn state is assembled - what gets in, what gets evicted.

ContextManager ResponseItem stream Prompt assembly Compaction (pre-turn / mid-turn) Token budgeting

The transcript lives in a single ContextManager that owns an ordered Vec<ResponseItem> - every user message, model response, tool call, and tool output - with a history_version counter bumped on rewrites and a reference_context_item that serves as the baseline for diffing settings changes between turns.

Each turn assembles a Prompt by stitching together the history items returned from ContextManager::for_prompt(), the active tool specs from the ToolRouter, base model instructions, and turn-specific personality / output-schema overrides.

Eviction is driven by compaction - when the rolling token estimate approaches the model's context window, the system summarizes earlier turns. InitialContextInjection distinguishes pre-turn compaction (full context will be reinjected before the next user message) from mid-turn compaction (the summary stands in for what came before the last user message).

A separate realtime_context layer pre-allocates fixed token budgets for the startup payload (current thread, recent work, workspace, scratch notes) so the cold-start prompt always fits.

  • codex-rs/core/src/client_common.rs:25 Prompt struct - the per-turn input payload: input, tools, base_instructions, personality, output_schema.
  • codex-rs/core/src/compact.rs:50 InitialContextInjection enum - controls whether a compaction summary embeds initial context (BeforeLastUserMessage) or defers re-injection (DoNotInject).
  • codex-rs/core/src/context_manager/normalize.rs History normalization - collapses adjacent items, repairs orphaned tool-call/tool-output pairs before the prompt is built.
  • codex-rs/core/src/realtime_context.rs:29 Startup token budgets - current thread (1200), recent work (2200), workspace (1600), notes (300).

Tools

Tool definitions, registry, and dispatch - from model output to handler invocation.

CoreToolRuntime trait ToolRegistry ToolRouter ToolOrchestrator JSON-Schema specs

Tools follow a trait-based dispatch pattern. Every locally executable tool implements CoreToolRuntime (provides metadata, telemetry tags, and the actual run entry point). Handlers are inserted into a ToolRegistry, which acts as the single source of truth for what the agent can do this turn.

When the model emits a tool call, ToolRouter::build_tool_call() parses the ResponseItem into a typed ToolCall (with ToolName, call_id, ToolPayload), then ToolOrchestrator::run() drives the full lifecycle: approval check → sandbox selection → execute → retry-with-escalation on denial → emit output back into the transcript.

Tool specs (JSON-Schema-validated input/output shapes) live in the tools/ crate so they can be shared between the core runtime and external consumers. Concrete handlers (shell, apply_patch, mcp, agent_jobs, ...) live under core/src/tools/handlers/.

  • codex-rs/core/src/tools/router.rs:34 ToolRouter - converts model ResponseItems into ToolCalls and routes by tool_name.
  • codex-rs/core/src/tools/orchestrator.rs:42 ToolOrchestrator - coordinates approval → sandbox selection → execution → retry sequence.
  • codex-rs/tools/src/tool_spec.rs ToolSpec - JSON-Schema-based spec shared with consumers outside the core crate.

Permissions & Sandbox

The Allow/Ask/Deny approval model plus the OS-level isolation mechanism.

execpolicy Decision ReviewDecision ApprovalStore macOS Seatbelt Linux bwrap + seccomp Windows restricted token + WFP

The approval layer is three pieces working together. execpolicy evaluates each command against rules and returns a Decision (Allow / Prompt / Forbidden). When a prompt is required, the user's response becomes a ReviewDecision (Approved, ApprovedForSession, ApprovedExecpolicyAmendment, NetworkPolicyAmendment, Denied, ...). Results are cached in the per-session ApprovalStore so repeated invocations don't re-prompt, and amendments can persist new prefix rules back into the user's execpolicy.

The sandbox layer is platform-pluggable through SandboxType: None, MacosSeatbelt, LinuxSeccomp, WindowsRestrictedToken. get_platform_sandbox() picks the default for the current OS, and the PermissionProfile is transformed into backend-specific CLI args / Seatbelt SBPL / Windows ACL + WFP rules at execution time.

Skills

Structured-prompt units - markdown + YAML frontmatter, loaded from layered roots.

SKILL.md format Layered discovery Progressive disclosure Scope: Repo > User > System > Admin

A skill is a directory whose SKILL.md file carries YAML frontmatter (name, description, metadata.short-description) plus a markdown body. Optional siblings - scripts/, references/, assets/, agents/openai.yaml - provide executables, lazily loaded docs, and output templates.

load_skills_from_roots() walks a layered set of roots in priority order: repo .agents/skills/, user $HOME/.agents/skills/, system cache, then any plugin-provided roots. Discovery is a bounded BFS (depth 6) that collects every SKILL.md, dedupes by path, and ranks duplicates by scope.

Loading is progressive: just the frontmatter is always in context, the full body is injected when the skill matches the active turn's description trigger, and bundled references/ / assets/ are pulled in only on demand.

Plugins

The extension model - manifest schema, install path, bundled capabilities.

plugin.json manifest Versioned cache dir Skills + MCP + Hooks + Apps [plugins] section in config.toml

A plugin is a versioned directory installed at $CODEX_HOME/plugins/cache/<marketplace>/<name>/<version>/ with sibling writable state at $CODEX_HOME/plugins/data/<name>-<marketplace>/. Users enable plugins by adding a [plugins] entry to config.toml keyed as "plugin-name@marketplace-name".

The manifest is a single plugin.json at the plugin root. Its Serde schema lives in core-plugins/src/manifest.rs: top-level fields cover name, version, description, keywords, plus references to bundled skills, mcp_servers, apps, and hooks; the interface block carries UI metadata (display name, icons, brand colour, screenshots, category, capability list).

load_plugins_from_layer_stack() reads the configured set, resolves the active version (latest semver, or "local" if present), and merges each plugin's bundled MCP servers, skill roots, apps, and hooks into the session's effective capability map. Plugins that fail to load surface in the load outcome but are marked inactive.

MCP - Model Context Protocol

Client, server registration, and transport types - bridging external tools into the registry.

McpConnectionManager Stdio transport StreamableHttp transport Tools merged into ToolRegistry

MCP servers are declared in TOML and parsed into McpServerTransportConfig, an enum with two transport variants:

  • Stdio - launches a subprocess with command, args, env vars, and cwd.
  • StreamableHttp - connects over HTTP with optional OAuth bearer token and custom headers.

McpConnectionManager is the control plane: it keeps a HashMap of running AsyncManagedClients keyed by server name, performs the Initialize / ListTools handshake, and routes every model tool call via call_tool_for_server(). External tools land in the agent's registry through effective_mcp_servers(), which unions the config-declared servers, any runtime-only additions (e.g. host-owned Codex Apps server), and the MCP servers exposed by enabled plugins.

Memory - AGENTS.md

The always-loaded instruction file at the repo root - discovery, walk, injection.

AGENTS.md (Codex) ≈ CLAUDE.md (Claude) Upward walk to project root .git as root marker Override file: AGENTS.override.md

Codex looks for AGENTS.override.md first, then AGENTS.md, plus any extra names configured via project_doc_fallback_filenames. The AgentsMdManager walks upward from config.cwd until it hits a project-root marker (default .git; configurable via project_root_markers; an empty list disables parent traversal so only cwd is scanned).

Every matching file from project root down to cwd is collected in that order and concatenated with the separator "\n\n--- project-doc ---\n\n". A global instruction file at ~/.codex/AGENTS.md (or its .override.md) is layered on top. The whole payload is capped by project_doc_max_bytes (truncated from the tail if exceeded), then injected as the UserInstructions fragment, wrapped in markers "# AGENTS.md instructions for <dir>" ... "</INSTRUCTIONS>".

The repo root itself ships an AGENTS.md (~17.5 KB) so the Codex working tree is itself an AGENTS-managed project.

Subagents

Dispatch a fresh agent instance with a bounded prompt and an isolated context.

spawn_agent tool AgentControl Fork or fresh context Depth-bounded

Subagents are dispatched as a tool call: the parent model invokes spawn_agent, which the runtime routes to handle_spawn_agent. The handler parses the arguments (model, reasoning_effort, agent_type/role, message, fork_context), checks the spawn depth against config.agent_max_depth, and calls AgentControl::spawn_agent_with_metadata() to materialize a new thread.

The new thread gets a freshly built Config via build_agent_spawn_config() - base instructions are inherited from the parent, then role-specific overrides are applied if an agent_type was provided, followed by runtime-state overrides (sandbox policy, approval policy, environment selections). SessionSource::SubAgent { ThreadSpawn { .. } } records the parent thread ID, depth, and role for hierarchical tracking.

Context is bounded: by default the child starts with an empty rollout; opt-in fork_context=true copies the parent's history. The parent and child share an AgentControl registry so the parent can later wait, resume, or close the child agent. Lifecycle is observed via CollabAgentSpawnBegin/EndEvent, CollabAgentInteractionBegin/EndEvent, and CollabAgentWaitingBegin/EndEvent.
