01

Context window

conversation state

How a turn is assembled before being sent to the model. Opencode runs an Effect-based pipeline that materialises the system prompt, walks the message history, expands attachments, splices in environment + skills + instructions, asks an overflow guard for headroom, and then either streams via the AI SDK or a native runtime. Eviction is two-stage: prune first (drop old tool outputs in place), then compact (LLM-summarise the tail).

Assembly

The system prompt is built fresh each turn - provider preamble, environment block, then memory and skills are concatenated and sent up front.

  • session/system.ts:19–33 picks the provider-specific base prompt (Anthropic / OpenAI / Gemini …) by model id
  • session/system.ts:48–63 environment() - cwd, git status, platform, date block
  • session/system.ts:65–77 skills() - emits the structured skill registry as text
  • session/llm/request.ts:54–186 LLMRequestPrep.prepare() - merges agent + provider + user system, applies plugin transforms, resolves enabled tools
  • session/message-v2.ts:630–691 toModelMessagesEffect() - serialises internal parts to AI SDK ModelMessage[], expands media, optionally strips it
  • session/reminders.ts:14–89 SessionReminders.apply() - splices plan-mode / build-mode reminders into the user turn

Eviction & compaction

An overflow guard runs every step; when it trips, opencode first prunes tool outputs in place, then runs a compaction LLM that rewrites the head into a summary.

  • session/overflow.ts:8–32 isOverflow() / usable() - compares input+output tokens against model.limit.input
  • session/compaction.ts:298–342 SessionCompaction.prune() - backward sweep that erases old tool outputs once PRUNE_PROTECT (40k) is exceeded, protecting the last 2 turns and skill outputs
  • session/compaction.ts:225–294 select() - picks the recent N turns within a token budget; splits the final turn if needed
  • session/compaction.ts:344–582 process() - strips media, runs the compaction agent with the summary template, tracks tail_start_id for replay
  • session/processor.ts:780–849 main loop polls llm.stream(), checks isOverflow() after each step, signals compaction

Streaming backend

Two backends sit side by side: the AI SDK for most providers, and a native runtime used for opencode-hosted models. Both normalise into a single LLMEvent stream.

  • session/llm.ts:81–341 LLM.run() - picks runtime, captures prepared messages, sets telemetry, dispatches
  • session/llm.ts:343–367 LLM.stream() - wraps run() with an AbortController and adapts events
  • session/llm/ai-sdk.ts:61–252 LLMAISDK.toLLMEvents() - converts Vercel AI SDK fullStream events to normalised LLMEvent
  • session/llm/native-runtime.ts:66–102 LLMNativeRuntime.stream() - opt-in path to @opencode-ai/llm for OpenAI / Anthropic / opencode

What's always in the window

The first message of every turn carries: the provider preamble, the environment block, all loaded AGENTS.md files (see §07), the skill registry (see §04), plugin-transformed tool definitions (see §02), and the message history minus pruned/compacted regions.

  • session/instruction.ts:154–168 Instruction.system() - assembles the AGENTS.md / CLAUDE.md / CONTEXT.md blob
  • session/prompt.ts:1435–1441 final stitch: [...env, ...instructions, ...skills] before message history
Eviction order matters: tool outputs are erased in place (cheap) before the compaction agent is ever called (expensive). The last two turns and any output from the skill tool are always protected.

Tools

define · register · invoke

A tool in opencode is an Effect-typed function with a parameter schema, an execute() body, and a Context handle that gives it a permission gate and metadata channel. Tool.define wraps every tool with validation, output truncation, and span tracing. A central registry assembles three sources - builtins, plugin tools, and MCP tools - and filters them per (provider, model, agent) tuple.

The Tool.define contract

Every tool is built through one helper so the framework gets to intercept arg decoding, error mapping, output truncation, and tracing in one place.

  • tool/tool.ts:149–167 Tool.define(id, effect) - returns Info<P, R>; the wrap() at :158 injects everything below
  • tool/tool.ts:34–44 Context - sessionID, messageID, agent, abort, ask(), metadata()
  • tool/tool.ts:46–51 ExecuteResult - title, metadata, output, optional attachments[]
  • tool/tool.ts:109–142 wrap body - schema decode → InvalidArgumentsError → execute → truncate() → span attrs
  • tool/truncate.ts:34–142 Truncate.output() - clips at max_lines / max_bytes, persists overflow to a tmp file referenced by hint
  • tool/invalid.ts:14–19 fallback tool returned when the LLM calls an unknown name or sends malformed JSON

Registry & dispatch

The registry is the only thing that knows about all three tool sources. It hands the loop a final list scoped to the current turn.

  • tool/registry.ts:73–80 Registry.Service - all(), tools(model, agent), named(), ids()
  • tool/registry.ts:199–220 plugin tools - scans {tool,tools}/*.{js,ts} via dynamic import, wraps via fromPlugin()
  • tool/registry.ts:225–244 builtins - shell, read, edit, glob, grep, write, task, … initialised in parallel
  • tool/registry.ts:316–361 tools() - filters per model+provider, fires "tool.definition" plugin hook, emits JSON schema
  • session/tools.ts:42–73 binds ctx.ask for each tool call to the session's permission ruleset
  • session/tools.ts:84–201 execution wrapper - fires tool.execute.before/after plugin hooks, bridges Effect→Promise for the AI SDK

Builtin tools - full lifecycle

Each builtin shows the pattern in miniature: a schema, an execute() that calls ctx.ask() before doing anything observable, and structured metadata for the UI.

  • tool/read.ts:29–37 schema - filePath (absolute), optional offset, limit
  • tool/read.ts:227–232 ctx.ask() gate before any byte is read
  • tool/edit.ts:69–208 string-replace edit - acquires file lock, asks for edit permission with diff in metadata, publishes File.Edited
  • tool/shell.ts:260–410 shell - parses bash with tree-sitter, expands vars/symlinks, collects every command-prefix and path that needs permission
  • tool/shell.ts:424–596 run() - spawns child process, streams stdout/stderr, races abort/timeout, truncates oversized output

Tool surface (what the model sees)

For a typical turn the registry exposes:

  • readwriteeditapply_patchglobgrep
  • shellwebfetchwebsearch
  • taskskilltodoplanquestionrepo_overviewlsp
  • … + any plugin tool + any MCP tool prefixed by server name

Permissions & sandbox

allow / ask / deny

The gate is a pattern-matched ruleset evaluated per tool call. Actions are allow / ask / deny; user replies are once / always / reject. There is, deliberately, no OS-level sandbox: shells inherit the user's full UID. Containment is application-level - every side-effectful tool calls ctx.ask() before acting, and shell commands are parsed so opencode can ask for each command-prefix and each path the script will touch.

The Allow / Ask / Deny machine

  • config/permission.ts:4 Action = "ask" | "allow" | "deny"
  • permission/index.ts:52 Reply = "once" | "always" | "reject"
  • permission/index.ts:22–50 Rule, Ruleset, Request schema definitions
  • permission/index.ts:171–211 Permission.ask() - evaluates every pattern; first deny wins, otherwise waits on user reply
  • permission/index.ts:213–269 reply() - once resolves now; always appends to approved and auto-resolves any pending request that now matches; reject rejects the chain
  • permission/evaluate.ts:1 re-exports the matcher from @opencode-ai/core/permission (glob + bash-arity)
  • permission/arity.ts:1–161 bash command-prefix table - git=2, npm run=3, docker compose=3, … used to normalise commands before matching
  • config/permission.ts:16–37 named permissions - read, edit, glob, grep, list, bash, task, external_directory, webfetch, websearch, skill

The "sandbox" (read the call-out)

  • shell/shell.ts:1–215 shells spawned via Node child_process.spawn; no Seatbelt, no bubblewrap, no restricted token, no seccomp
  • shell/shell.ts:10–20 META table - only marks incompatible shells (fish, nu) as deny: true
  • shell/shell.ts:28–57 killTree() - platform-aware process-tree teardown (taskkill on Windows, signals on Unix)
  • tool/external-directory.ts:16–44 assertExternalDirectory() - the only path-boundary check, and it's just another ctx.ask()
  • agent/subagent-permissions.ts:17–34 deriveSubagentSessionPermission() - subagents inherit parent denies; todowrite and task default-denied
  • tool/shell/prompt.ts:22–34 shell params - command, optional timeout, workdir, description; no sandbox flag
The sandbox is the permission prompt. Opencode does not use Seatbelt, bubblewrap, restricted tokens, seccomp, or any other OS-level confinement. Once a shell call is approved, the child process runs with the user's full privileges - it can read, write, and network anywhere. Containment is built entirely on (a) parsing shell commands to surface every command-prefix and every path for permission, and (b) every other tool calling ctx.ask() before doing anything observable. If you want real isolation, run opencode itself inside a container or VM.

Skills

structured prompt unit

A skill is a SKILL.md file - YAML frontmatter (name, description) plus a markdown body. All discovered skills are listed in the system prompt; the model invokes one by calling a single skill tool with the skill's name. The tool's output is the skill body wrapped in XML, plus a directory listing so the skill can reference its own bundled assets.

File format & discovery

  • skill/index.ts:52–58 isSkillFrontmatter() - validates name (required) + description (optional) YAML
  • skill/index.ts:186–194 looks in ~/.claude/skills/, ~/.agents/skills/ (pattern skills/**/SKILL.md)
  • skill/index.ts:196–202 walks up from cwd to worktree root checking .claude/ and .agents/
  • skill/index.ts:210–227 config-driven paths and URLs - config.skills.paths[] + config.skills.urls[]
  • skill/index.ts:274–279 built-in skill - customize-opencode registered first, overridable by disk
  • skill/discovery.ts Discovery.pull() - fetches remote skill packs via HTTP index.json
  • config/skills.ts:3–10 user-facing schema - skills: { paths?, urls? }
  • skill/prompt/customize-opencode.md the bundled example skill

Invocation

Skills do not become individual tools. They share one skill tool with a name parameter.

  • tool/skill.ts:14–22 schema - single name: string that must match a discovered skill
  • tool/skill.ts:23–69 execute - skill.require(), ctx.ask(), list bundled files, render XML output
  • tool/skill.ts:47–63 output shape - <skill_content name="…"> wrapping the body + base directory + up to 10 bundled files
  • tool/skill.txt LLM-facing description: "Load a specialized skill when the task matches…"
  • session/system.ts:65–77 skill catalogue rendered into the system prompt so the model knows what's invokable
Skill outputs are protected from the prune sweep - see context-window §01: compaction.ts:298–342. Once the model has loaded a skill, that reference stays in the window even as older tool outputs are erased.

Plugins

extension model

A plugin is an npm package or local file that default-exports a function returning a Hooks object. Hooks cover events, config, tools, auth/provider registration, chat-message / chat-params / chat-headers transforms, tool before/after hooks, and shell-env injection. Plugins are dynamic-imported at startup and triggered sequentially so registration order is deterministic.

Plugin contract

  • packages/plugin/src/index.ts:74–80 Plugin = (input, options?) => Promise<Hooks>; optional PluginModule { id?, server }
  • packages/plugin/src/index.ts:56–66 PluginInput - client SDK, project context, shell access
  • packages/plugin/src/index.ts:222–333 Hooks interface - event, config, tool, auth, provider, chat.message, chat.params, chat.headers, tool.execute.before/after, shell.env

Loader pipeline

  • plugin/index.ts:58 Plugin.Service - the init() entrypoint that loads everyone and collects hooks
  • plugin/index.ts:215–276 sequential apply - keeps registration deterministic; trigger<Name> dispatches across plugins
  • plugin/loader.ts:85–235 resolve target → detect entry (./server in package.json#exports) → semver check engines.opencode → await import(entry)
  • plugin/install.ts npm install path for remote plugins (delegates to Npm.add())
  • plugin/shared.ts:103–213 PluginKind, file/npm resolution, checkPluginCompatibility
  • plugin/meta.ts package metadata extraction

Config schema

Plugins are declared in opencode.json as a flat array of specs (npm, npm+options, or file://).

  • config/plugin.ts:1–85 spec types - string, [name, options], or file://./path; deduplication by package name or URL
  • config/plugin.ts:29–36 local discovery - auto-scans {plugin,plugins}/*.{ts,js} next to the config

Bundled examples (auth plugins)

  • plugin/github-copilot/ device-code OAuth flow for GitHub Copilot; injects custom chat.headers
  • plugin/azure.ts:1–26 simplest auth plugin shape - API key prompt
  • plugin/codex.ts · cloudflare.ts · digitalocean.ts · xai.ts more provider plugins bundled by default; disabled via flags.disableDefaultPlugins

MCP

Model Context Protocol client

Opencode is an MCP client. It connects to user-configured MCP servers across three transports - stdio, Streamable HTTP, SSE - and hoists every server's tools into the same registry as builtins. Remote transports get an OAuth provider with dynamic client registration; tokens land in mcp-auth.json.

Transports & registration

  • mcp/index.ts:4–6 imports - StreamableHTTPClientTransport, SSEClientTransport, StdioClientTransport
  • mcp/index.ts:282 Transport union - three-way discriminated
  • mcp/index.ts:421–454 connectLocal() - spawns subprocess via stdio with cwd + env injection
  • mcp/index.ts:304–419 connectRemote() - tries StreamableHTTP, falls back to SSE; surfaces needs_auth / needs_client_registration
  • mcp/index.ts:456–481 create() - top-level dispatcher: local vs remote
  • mcp/index.ts:93–99 status union - connected | disabled | failed | needs_auth | needs_client_registration
  • mcp/index.ts:533–581 init & finalizer - boots configured servers, kills child descendants on shutdown

Tool integration

  • mcp/index.ts:128–155 listTools() - queries the server with a tolerant fallback schema
  • mcp/index.ts:158–186 convertMcpTool() - wraps an MCP tool as AI SDK dynamicTool
  • mcp/index.ts:663–696 tools() - collects per-server tools, prefixes them by sanitised server name, filters to status: "connected"
  • mcp/index.ts:508–520 watch() - subscribes to ToolListChanged, publishes ToolsChanged on the bus

Config schema

What the user writes in opencode.json to add a server.

  • config/mcp.ts:4–19 local - { type: "local", command: [...], environment?, enabled?, timeout? }
  • config/mcp.ts:39–55 remote - { type: "remote", url, headers?, oauth?, enabled?, timeout? }
  • config/mcp.ts:21–37 OAuth subconfig - clientId?, clientSecret?, scope?, callbackPort (default 19876)

OAuth ceremony

  • mcp/oauth-provider.ts:29–196 implements MCP's OAuthClientProvider; RFC 7591 dynamic client registration; refresh + expiry
  • mcp/oauth-callback.ts:141–170 local callback server on http://127.0.0.1:19876/mcp/oauth/callback; 5-min CSRF-state-validated window
  • mcp/auth.ts:23–80 tokens persisted to mcp-auth.json keyed by server name with URL validation
  • mcp/index.ts:771–886 startAuth() → authenticate() → finishAuth() three-step ceremony
  • tool/mcp-websearch.ts an MCP-backed builtin - direct JSON-RPC POST to an HTTP MCP server
07

Memory - AGENTS.md handling

always-loaded instructions

Opencode treats AGENTS.md as its canonical instruction file, with CLAUDE.md and CONTEXT.md as fallbacks. Discovery is a two-tier walk: a global layer under ~/.config/opencode/ (and ~/.claude/), then a project layer that uses findUp from the cwd to the worktree root - first match wins. On every file read, opencode also walks the file's directory upward to splice in nearby per-folder instruction files.

Filenames & discovery

  • session/instruction.ts:14–18 filename priority - AGENTS.md → CLAUDE.md (if !disableClaudeCodePrompt) → CONTEXT.md
  • session/instruction.ts:64–88 global layer - ~/.config/opencode/AGENTS.md and ~/.claude/CLAUDE.md
  • session/instruction.ts:122–131 project layer - fs.findUp() from cwd to worktree root; first match wins (no stacking of every ancestor)
  • session/instruction.ts:134–149 custom config.instructions[] - local globs, absolute paths, or http(s):// URLs with 5s timeout

Injection & nested attach

  • session/instruction.ts:109–152 systemPaths() - full resolved list of instruction files
  • session/instruction.ts:154–168 system() - reads each and yields Instructions from: {path}\n{content} blocks
  • session/instruction.ts:170–176 find() - locate the first instruction file in a single directory
  • session/instruction.ts:178–220 resolve() - on each file read, walks the file's directory upward to the worktree and attaches any nearby AGENTS.md, once per message
  • session/prompt.ts:1435–1441 final stitch into the system prompt: [...env, ...instructions, ...skills]
  • AGENTS.md the repo's own top-level instructions - proof of dogfooding
First match wins. If you have an AGENTS.md in ~/.config/opencode/ and another at the repo root, both load - global + project. But within the project walk, only the first AGENTS.md found between cwd and the worktree root is picked. Per-subdirectory instructions get layered in dynamically when files in those subdirs are read.

Subagents

isolated dispatch

The task tool spawns a fresh session - separate message history, its own system prompt from the picked agent, its own permission ruleset derived from the parent - and returns the subagent's final reply as a single string to the parent. Subagents can be invoked synchronously or backgrounded via background: true.

Dispatch

  • tool/task.ts:47–52 params - description, prompt, subagent_type, optional task_id (resume), optional background
  • tool/task.ts:143–159 creates a new session with parentID linking back; derives restricted permissions via deriveSubagentSessionPermission()
  • tool/task.ts:164–167 model - subagent's model override wins; otherwise inherits parent's (providerID, modelID)
  • tool/task.ts:184–200 isolated context - fresh messageID, fresh message history scoped to the new session; forces tool restrictions (todowrite, task) unless explicitly enabled
  • tool/task.ts:273–278 result flow - sync (foreground) or async (background) reply returned as <task> XML carrying the session id
  • tool/task.txt LLM-facing description of when to delegate to a subagent

Agent.Info & built-in agents

  • agent/agent.ts:29–50 Agent.Info - name, mode: "subagent" | "primary" | "all", permission, optional model / prompt / temperature
  • agent/agent.ts:384–451 Agent.generate() - LLM-synthesises a new agent definition from a description (returns { identifier, whenToUse, systemPrompt })
  • agent/subagent-permissions.ts:17–34 deriveSubagentSessionPermission() - child inherits parent agent's edit denies, parent session denies, and gets default-denies for todowrite + task
  • agent/prompt/explore.txt read-only exploration agent - grep/glob/read only
  • agent/prompt/scout.txt experimental dependency/docs scout with repo-clone capability
  • agent/prompt/compaction.txt · summary.txt · title.txt internal primary-mode agents the loop drives itself (compaction, summary, title)
  • agent/generate.txt system prompt used when synthesising new agent definitions
Privilege monotonicity. A subagent can never do something its parent agent's ruleset forbade - denies cascade. It also can't recursively spawn its own task calls or write to the parent's todo list unless the agent definition explicitly re-enables them.

Additional primitives that emerged

beyond the eight

Plan / build mode

CLI & server entry

  • cli/bootstrap.ts runtime bootstrap
  • server/server.ts · event.ts local HTTP + bus→SSE bridge for desktop, web, remote clients
  • lsp/lsp.ts LSP client - language servers feeding diagnostics into the lsp tool and edit results
  • snapshot/index.ts repo snapshots used by session/revert.ts for undo
